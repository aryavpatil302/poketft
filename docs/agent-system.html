PokéTFT Agent System

Living Doc Design reference and learning guide for the AI-powered balance engine. Updated as the system is built.

What Are Agents?

An AI agent is a program that uses a language model (like Claude) not just to answer a question, but to take actions — call functions, read data, make decisions, and loop until a goal is reached.

The key difference between a plain LLM call and an agent:

Plain LLM call

You send a prompt, Claude replies with text. One shot. No memory of what happened before. Can't run code or fetch data.

Agent

Claude decides to call a tool (e.g. run_simulation), gets back structured data, reasons about it, maybe calls another tool, then produces a final output.

Core Concept
The model doesn't just talk about balance — it runs experiments, reads the results, and proposes changes backed by data. The language model handles reasoning; deterministic code handles computation.

Why Agents for Balance?

TFT balance is hard for humans because the search space is enormous. A single damage change on one unit affects hundreds of matchups across all tier levels, synergy combinations, and item configurations.

Agents solve this by:

  • Scale — running thousands of simulations quickly, far more than any human play-tester
  • Consistency — applying the same evaluation criteria every time, with no fatigue or bias
  • Explainability — every proposal cites the simulation data that motivated it
  • Iteration speed — a full balance pass that would take days of play-testing runs in minutes

Three-Layer Architecture

┌──────────────────────────────────────────────────────────┐ │ BALANCE ENGINE │ │ │ │ Layer 1: Simulation Agents │ │ Run matchups → collect raw stats │ │ ↓ │ │ Layer 2: Analysis Agents │ │ Read stats → flag problems → explain why │ │ ↓ │ │ Layer 3: Proposal Agents │ │ Suggest concrete number changes → vote → apply │ └──────────────────────────────────────────────────────────┘ ↑ All layers call into ↓ ┌──────────────────────────────────────────────────────────┐ │ Game Engine (TypeScript) │ │ run_simulation(), get_unit_definition(), etc. │ └──────────────────────────────────────────────────────────┘

Each layer is independent — a simulation agent doesn't know about proposals, a proposal agent doesn't run simulations itself (it calls the tool). This keeps each agent small, focused, and easy to debug.

Layer 1 — Simulation Agent

The simplest agent. Its only job is to decide which matchups to run and then call run_simulation on each. It returns structured data, not text.

What it does

  • Given a unit ID (or a list), generates a set of representative matchups (different enemy compositions, tier levels)
  • Calls run_simulation repeatedly — typically 100 trials per matchup to get statistically stable win rates
  • Stores results tagged with the unit, tier, synergy context, and timestamp

Why it needs to be an agent and not just a script

A pure script would need to enumerate every possible matchup manually. An agent can reason about which matchups are most informative — for example, testing a tank unit against high-damage ranged units first, because that's the matchup most likely to reveal balance problems. The LLM handles that prioritization; the script just runs whatever it's told.

How it's built
A single Claude API call with tool_use enabled. The system prompt explains TFT matchup coverage. The model outputs a series of run_simulation tool calls. Our code executes each call against the game engine and feeds results back. The model continues until it decides coverage is sufficient.

Layer 2 — Analysis Agent

Reads simulation data and flags issues. This is where the LLM's reasoning is most valuable — translating raw numbers into a human-readable problem statement with evidence.

Example output

AnalysisResult {
  unit: "vikavolt",
  severity: "high",
  issue: "Vikavolt T3 wins 78% of matchups across all enemy compositions tested.
         Discharge deals 675 damage to an entire row — at T3 this one-shots
         most non-tank units. Combined with a 3-second stun, the ability
         effectively ends combat on cast.",
  evidence: {
    avg_win_rate: 0.78,
    worst_matchup: { enemy: "tropius + venusaur + tangela", win_rate: 0.61 },
    ability_proc_rate: 1.2, // fires 1.2 times per combat on average
  },
  suggested_investigation: "Reduce base damage or stun duration. Do not touch both at once."
}

Layer 3 — Proposal Agent

Takes a flagged analysis and produces a concrete, testable change. It must also run a run_simulation_with_patch to verify the proposed change actually improves the numbers before submitting.

The loop

Proposal Agent receives: AnalysisResult (unit + issue + evidence) 1. Reason about the root cause "Damage too high? Stun too long? Both? Attack speed letting it cast too often?" 2. Hypothesize a minimal change "Lower T3 damage from 675 → 550. Leave stun unchanged." 3. call run_simulation_with_patch(patch, trials=200) Verify win rate drops to acceptable range (~50–55%) 4. If still broken → iterate (adjust patch, re-run) Max 3 iterations to avoid runaway loops 5. Submit proposal with evidence from both before and after
Why the agent runs its own verification
Without self-verification, proposals are just guesses. By requiring the agent to call run_simulation_with_patch before submitting, every proposal arrives with proof that it actually fixes the problem — not just a theory.

How Claude API Calls Work

Every agent is built on the same foundation: a call to anthropic.messages.create(). Here's the full structure: 

const response = await anthropic.messages.create({
  model: "claude-opus-4-8",

  // system: who this agent is and what "good" looks like
  system: `You are a TFT balance analyst. A healthy unit wins 45–55% of matchups
    across a representative set of enemy compositions. Flag anything outside
    this range as a problem. Always cite specific simulation data.`,

  // messages: the conversation so far (starts with just the task)
  messages: [
    { role: "user", content: "Analyse Vikavolt's balance using available simulation data." }
  ],

  // tools: what the model is allowed to call
  tools: [getSimulationHistory, runMatchupMatrix],

  // how many tokens the model can think + respond with
  max_tokens: 4096,
})

The response comes back with either a text block (the model's final answer) or a tool_use block (the model wants to call one of your tools). Your code handles the tool call, runs it, sends the result back, and loops until the model produces a final text response.

Tool Use — The Core Mechanism

Tool use is how agents interact with the real world. The model can't run simulations itself — it outputs a structured request, and your code runs the actual function.

Your code Claude → "Analyse Vikavolt" + tool list ← tool_use: run_simulation_history { unit_id: "vikavolt", days: 30 } → tool_result: { win_rates: [...] } ← tool_use: run_matchup_matrix { unit_ids: ["vikavolt", "tangela", ...] } → tool_result: { matrix: [...] } ← text: AnalysisResult { ... }

The key insight: the model decides when to call tools and in what order. You don't hard-code "call this tool, then that one." The model reads its system prompt, understands what tools are available, and figures out the right sequence to gather the information it needs.

Structured Output

Agents need to return machine-readable data, not prose. The cleanest way to enforce this with Claude is to define a tool called something like submit_analysis and tell the model it must call that tool to finish its task. 

// Instead of asking Claude to "write an analysis", tell it to call this:
{
  name: "submit_analysis",
  description: "Submit your completed analysis. You must call this to finish.",
  input_schema: {
    type: "object",
    properties: {
      unit:     { type: "string" },
      severity: { type: "string", enum: ["low", "medium", "high"] },
      issue:    { type: "string" },
      evidence: { type: "object" },
    },
    required: ["unit", "severity", "issue", "evidence"]
  }
}

This pattern — a "submit" tool with a strict schema — guarantees your output is always parseable JSON, never free-form text you'd need to parse manually.

Stateless Design

Each agent run starts fresh — no memory of previous runs. All state lives in your database, not in the model's context.

This is intentional:

  • Makes agents cheap to run (short context = lower cost)
  • Makes failures recoverable (re-run from any point)
  • Keeps agents from accumulating biases across runs
  • Lets you run multiple agents in parallel without interference
Common mistake
Don't try to pass the previous agent's full output to the next agent as context. Pass only what's relevant — the analysis result, not the raw simulation data. Long context is slower and more expensive, and the model can get confused by noise.

Deterministic Tools

These are the functions agents can call. They are pure, deterministic code — the same input always produces the same output (modulo RNG in simulations, which is handled by running many trials and returning averages).

The separation is important: the model does reasoning, the tools do computation. You never want the model to guess a damage number — you want it to call run_simulation and read the actual result.

Tool Input Returns
run_simulation player units, enemy units, # trials win rate, avg ticks, damage breakdown, ability proc count
run_simulation_with_patch same + a list of stat overrides same, but applied with the proposed changes
run_matchup_matrix list of unit IDs NxN win rate table for all pairwise combinations
get_unit_definition unit ID current stats, ability values, traits, tier scaling
get_simulation_history unit ID, days win rate over time — shows whether unit is drifting
get_trait_units trait ID all units in the trait + active thresholds
get_open_proposals — all proposals awaiting votes
submit_proposal unit, field, old value, new value, reasoning, evidence run ID proposal ID
cast_vote proposal ID, vote (approve/reject), reasoning updated vote tally

Tool Schemas (JSON Schema)

Every tool needs a JSON Schema definition so Claude knows exactly what arguments it can pass. Here's a full example: 

{
  "name": "run_simulation_with_patch",
  "description": "Run combat simulations with temporary stat overrides applied.
    Use this to test whether a proposed balance change actually improves win rates
    before submitting it as a proposal.",
  "input_schema": {
    "type": "object",
    "properties": {
      "player_units": {
        "type": "array",
        "items": { "type": "object",
          "properties": {
            "id":   { "type": "string" },
            "tier": { "type": "integer", "enum": [1, 2, 3] }
          }
        }
      },
      "enemy_units": { "type": "array", "items": { "$ref": "#unit" } },
      "patch": {
        "type": "array",
        "description": "Stat overrides to apply before running",
        "items": {
          "type": "object",
          "properties": {
            "unit_id": { "type": "string" },
            "field":   { "type": "string",
              "description": "e.g. 'ability.damageValues[2]' or 'baseStats.attack'" },
            "value":   { "type": "number" }
          },
          "required": ["unit_id", "field", "value"]
        }
      },
      "trials": { "type": "integer", "default": 100 }
    },
    "required": ["player_units", "enemy_units", "patch"]
  }
}

The description fields matter a lot — they tell the model when to use this tool and how to use it correctly. Bad descriptions lead to the model calling tools with wrong arguments.

The Upvoting / Voting System

A single agent proposing and applying its own changes is dangerous — it might "fix" a problem in one matchup while breaking three others. The voting system adds a layer of independent review before anything changes.

How it works

  1. A Proposal Agent submits a change with evidence
  2. Four specialized Voter Agents each receive the proposal independently
  3. Each voter runs run_simulation_with_patch on their own to verify the claim
  4. Each voter casts a typed vote: approve, reject, or abstain with reasoning
  5. If 3 of 4 approve → the change is applied (or queued for human review)
  6. If any voter rejects with a new finding → a new analysis cycle begins

Example vote tally

Proposal: Vikavolt T3 damage 675 → 550
Early Game Agent
✓ approve
Late Game Agent
✓ approve
Synergy Agent
~ abstain
Counterplay Agent
✓ approve

→ Passed 3/4 — change applied

Voter Agent Roles

Each voter agent has a different system prompt that gives it a distinct perspective. The goal is to cover blind spots that a single agent would miss.

Agent Focus What it checks
Early Game Agent Tier 1 & first cast Is the unit too strong / weak at 1-star? Does it first-cast too early or too late?
Late Game Agent Tier 3 scaling Does T3 feel game-winning but not instantly win? Is the T3 numbers spike proportionate?
Synergy Agent Trait interactions Does this change break a trait combo? Does it buff jungle/volcanic/etc. too much?
Counterplay Agent Counterplay options After this change, is there still a way to beat the unit? Or does it become unanswerable?

Blind vs Open Voting

In blind voting, voters don't see each other's votes before casting. In open voting, they do.

Blind voting

Each agent reaches its conclusion independently. No anchoring bias — the Late Game Agent can't just agree with the Early Game Agent because it saw that vote first. More honest signal.

Open voting

Agents can see dissenting opinions and respond to them. Useful for catching genuine conflicts ("this helps early game but I found it breaks Jungle trait at T3"). More nuanced but risks groupthink.

Open Question
Which mode to use, or whether to do a hybrid (blind first round, open second round if there's a split) — TBD.
